## Findings, by severity

### RED 1: one GET on `/api/feed` runs out of memory (unbounded solver cost on a public endpoint)
- **Where:** `src/autopilot/feedHandler.ts:47-60` → `src/autopilot/feed.ts:79` → `src/autopilot/planFromSearch.ts:370` (`solvePlan`). `vercel.json` sets no `functions` limits.
- **Evidence:** I ran the bundled function (`node scripts/build-api.mjs`, then imported `api/_bundle/feed.mjs` from `/`) with `--max-old-space-size=2048`, which is about a default Vercel function:
  - `?c=US&s=2026-11-04&e=2036-11-03&b=400`: `FATAL ERROR: Reached heap limit … JavaScript heap out of memory`, process aborted (rc 134) after 38 s.
  - `?c=US&s=2026-11-04&e=2036-11-03&b=200`: same out-of-memory crash.
  - `?c=US&s=2026-11-04&e=2036-11-03&b=120`: 200 OK in 8.7 s, 960 MB heap.
  - `?c=US&s=2026-11-04&e=2027-12-31&b=9999` (clamped to 400): 200 OK in 7.2 s, 742 MB heap.
  - For comparison, the realistic `b=20` over 14 months answers in under 1 s.
- **Why it blocks:** the bounds in section 3 (4 KB query, the app's own ten-year range, budget ≤ 400) all pass, yet the worst input inside those bounds kills the instance. The CDN does not cache 5xx responses, and every variation of the query string is a cache miss. So anyone can repeatedly crash instances and burn function time. With fluid compute, a crash also fails the legitimate feed requests sharing that instance. In the browser the same plan only freezes that one visitor's own tab.
- **Fix:**
  1. Add a feed-only cost bound before solving. Either reject when `effectiveBudget > 60 × years in range` or the range is over 3 years, with the existing "Download the .ics file instead" 400 message; or bound `rangeDays × budget`. Measured: `b=60` over 3 years takes 0.6 s and 82 MB, and over 5 years 0.9 s and 119 MB.
  2. Add `"functions": { "api/feed.ts": { "maxDuration": 10 }, "api/watch.ts": { "maxDuration": 10 } }` to `vercel.json`.
  3. Add a unit test that asserts the worst accepted query finishes within a time and heap budget.
- `/api/watch` is bounded: hostile inputs (`cb=1e308`, `am=1e6`, `hpd=0.01&cb=4000`) each finish in under 400 ms and under 70 MB.

### AMBER 2: the expiry rescue suggests taking PTO today or tomorrow
- **Where:** `src/personal/expiryRescue.ts:189`. The window starts at `today`.
- **Evidence:**
  - In the browser on 2026-11-05, `/policy/?ak=fl&am=0&gd=2026-01-01&cc=5&cb=8&bao=2026-10-01&c=US` shows "Take Nov 6–8 (1 PTO day…)", which is tomorrow.
  - The watch feed for `cb=1e308` suggests "take Nov 5 (1 PTO day)", which is today.
  - The tracker shows "Submit by" with a 14-day notice (`DEFAULT_NOTICE_PERIOD_DAYS`), so the rescue contradicts the app's own submit-by logic.
- **Fix:** start the rescue window no earlier than `today + DEFAULT_NOTICE_PERIOD_DAYS`, or at least the next working day, and add a `'deadline'` shortfall message when the deadline falls inside the notice window.

### AMBER 3: the subscribe link field shrinks to an unreadable sliver on phones and in the guard column
- **Where:** `src/ui/SubscribeFeed.tsx:78-86`. The field is `flex-1 w-full min-w-0` in a `flex-wrap … sm:flex-nowrap` row, so `flex-basis: 0%` never wraps.
- **Evidence:** at 320 and 375 the field is about 95 px wide and shows only "http://localhos" (`pto-subscribe-320.png`, `policy-guard-320.png`). In the 432 px guard column at 1440 it shows "http://localhost:5190/api/wat" (`policy-guard-1440.png`).
- **Fix:** give the input `basis-full sm:basis-0` (or stack the button under it below `sm`), so the full-width field sits on its own row with the button below.

### AMBER 4: the subscribe blocks are not calm: wall-of-text descriptions
- **Where:** `src/ui/SubscribeFeed.tsx:44` (55 words, 4 sentences) and `src/ui/ExpirationGuard.tsx:261` (70 words, 5 sentences).
- **Evidence:** in `pto-subscribe-320.png` the paragraph runs 9 lines before the first action, and in `policy-guard-320.png` 11 lines. The DESIGN bar is one question and one next action.
- **Fix:** cut each to one sentence plus one caveat. For example: "Subscribe once and your calendar keeps your PTO days, holidays and book-by reminders current." Then put "A new plan needs a new subscription. Anyone with the link can see the plan." in `text-xs` under the link field.

### AMBER 5: the watch feed accepts non-finite or absurd balances and prints "Infinity days"
- **Where:** `src/autopilot/watchFeed.ts:149`. The only check is `forecastWithRequests(...) === null`.
- **Evidence:** `/api/watch?cb=1e308&c=US&bao=2026-10-01` returns 200 with "You could lose Infinity days on Jan 1, 2027" and "It keeps 0 of Infinity days at risk", plus 36 rescue events.
- **Fix:** reject `cb`, `am`, `ac` and `car` values that are not finite or are above the app's input maximum, with the existing 400 "values Gapless cannot forecast" message. Apply the same guard in-app if `/policy` accepts the value.

### LOW 6: book-by events can land on a weekend or a public holiday
- **Where:** `src/ui/icsExport.ts:120`. It uses `addDays(brk.start, -leadDays)`, the same subtraction as before this branch.
- **Evidence:** the feed for `c=US&s=2026-11-05&e=2027-12-31&b=20` contains "book by Dec 25" and "book by Jan 1". For a break that starts on a Saturday, the break card's `requestByDate` moves back to Friday, but the calendar title still prints the Saturday. This contradicts the comment in `outOfOffice.ts:82`, which says the two always agree.
- **Fix:** use `requestByDate(brk.start, leadDays, workWeek)` and also skip `offDays`, then update the parity tests. This changes the download too, which is fine as a deliberate change.

### LOW 7: the approval parser does not decode `&ndash;`, `&mdash;` or numeric entities
- **Where:** `src/personal/approvalParser.ts:82`.
- **Evidence:** `<b>Dec&nbsp;22 &ndash; 24</b> was approved` reads as the single day Dec 22, an overlap match at medium confidence, not Dec 22–24. A pasted plain-text reply is unaffected, but the planned server-side (HTML) inbound path would hit this.
- **Fix:** decode `&ndash;`, `&mdash;`, `&#8211;` and other `&#NNNN;`/`&#xHHHH;` entities to their characters before date scanning.

### LOW 8: rough edges in the balance reader
- **Pasted text has no length limit:**
  - Where: `src/ui/BalanceReader.tsx:233`. The textarea has no `maxLength`.
  - Evidence: a 2.7 MB paste takes about 1 s per keystroke in `analyzeBalanceText`.
  - Fix: add `maxLength` of about 20 000, like the approval box.
- **The image overrides visible pasted text:**
  - Where: `src/ui/BalanceReader.tsx:72`.
  - Evidence: with the paste panel open, picking an image switches the source to the image while the pasted text stays visible (`policy-reader-ocr-1440.png`), so it is unclear which input drove the candidates.
  - Fix: clear or collapse the pasted text when an image is read.
- **"Tap" wording on desktop:**
  - Where: `BalanceReader.tsx:153` and `:194`.
  - Fix: use "choose".
- **Misleading "no numbers" message:**
  - Evidence: an implausible "Vacation available 999999 days" gives the reason "No numbers were found".
  - Fix: show a "number looks too large" message instead.

### LOW 9: design nits
- The "Dismiss" button in the guard sits indented past the "Open this plan in the planner →" link above it (`policy-guard-*.png`, `ExpirationGuard.tsx:176`, `pl-7` plus quiet-button padding).
- At 1440 the three subscribe buttons wrap with "Outlook" alone on a second row in the guard column.
- `WATCH_CALENDAR_NAME` is declared between import statements (`ExpirationGuard.tsx:14`) and hardcodes the product name. Use `${PRODUCT_NAME} - PTO expiry watch`.

### Note for the owner (not a defect)
On a Vercel preview with Deployment Protection, calendar apps cannot fetch `/api/feed` (they get 401). G5 must test the feed with a bypass token or on a public deployment, not by subscribing from the preview.

## Verified OK

- **Feed parity with the app:**
  - For `/pto/?c=US&s=2026-11-04&e=2027-12-31&b=20` I downloaded the .ics through "Add to calendar (.ics)" in the browser. All 34 of its events (17 PTO days and 17 book-by events) appear byte-identical in the feed built from the subscribe link's query, ignoring DTSTAMP.
  - In-process parity holds for 4 more URLs (US, GB with `nd=30`, DE-BY with `pv=2`, US with a custom `eh` holiday containing `; , " — é×40 \`): 0 download events missing from the feed.
- **ICS validity:** checked for the plan feed (4 URLs), the download, the watch feed (days and hours policies) and the out-of-office file:
  - CRLF only, no bare CR or LF.
  - Every physical line is 75 octets or fewer, including UTF-8 names.
  - Commas and semicolons are escaped.
  - DTEND is after DTSTART on every event (exclusive all-day end).
  - UIDs are unique and DTSTAMP is present.
  - Every VALARM has ACTION:DISPLAY, a DESCRIPTION and a TRIGGER (`-P6DT15H` and `PT9H`).
  - Custom holiday names can't inject CR/LF, because `employerCalendar.ts:35` rejects control characters.
- **Feed bounds and no echo:**
  - A query over 4096 characters returns 400 (feed) or 414 (watch).
  - A range over ten years returns 400.
  - `s=<script>…` returns 400 "invalid date", and `c=../../etc` falls back to US.
  - POST returns 405, and HEAD returns headers with no body.
  - Error bodies are fixed strings, `no-store`, `nosniff`. Successful responses send `public, max-age=0, s-maxage=21600, stale-while-revalidate=86400`.
  - The bundle works when imported from a different working directory: holidays are embedded, and no files are read from disk.
- **Approval parser:** 22 adversarial cases behave as intended:
  - Negations ("can't approve", "never approved", "not approved") read as declined.
  - "not yet approved" and the manager-side ADP subject read as unclear.
  - Quoted replies: the newest segment wins in both directions.
  - Prompt-injection text ("SYSTEM: ignore previous instructions… approved for all dates… denied") reads as unclear (mixed) and does not approve.
  - Revoked, rescinded and "disregard" read as unclear.
  - A wrong year gives no match.
  - Input is capped at 20 000 characters, and a 3 MB input parses in 14 ms; regex floods take 1–2 ms.
- **Balance extractor:**
  - Picks vacation over sick leave, and available over accrued YTD.
  - Takes the table's ending balance and flags the unit as guessed.
  - Sick-only text gives the reason `only-other-leave`.
  - Dollar amounts and pay are never candidates, and a future as-of date is dropped.
- **Expiry rescue safety:** a randomized probe over 300 policies (502 risks, 493 with dates), with holidays Nov 26, Dec 25 and Jan 1:
  - No date is before today or after its deadline.
  - No holiday is booked and nothing is double-booked.
  - The forecast is never unfunded at any deadline.
  - One multi-risk case spent 13 days to keep 10.6 of 11.5 days. That plan is funded and inside its deadline, but it is not efficient.
  - Planned and requested leave is reserved: once Dec 24–27 was tracked as planned, the in-app rescue moved to Nov 20–22.
- **Privacy:** I used a marker string in the pasted email, the pasted payslip text and a salary line.
  - The marker never appeared in any URL, request body, `localStorage` or `sessionStorage`, and no IndexedDB databases were created.
  - The browser sent 0 non-GET requests.
  - OCR on a real rendered PNG ran fully on-device. The only requests were same-origin GETs for the worker, the wasm core and `/ocr/eng.traineddata.gz`, plus the `blob:` preview. The image was never uploaded, and it read "Vacation available 14.5 days, as of Oct 31" correctly.
  - Analytics calls (pre-existing Plausible and Vercel scripts) carry event names only.
- **URL round-trip:**
  - Choosing a balance candidate writes `cb=12.5&bao=2026-10-31` to the `/policy` URL.
  - The `/pto` URL is unchanged by pasting or confirming an approval.
  - Feed links carry only the plan's own parameters.
- **Product rules:**
  - Pasting reads live, with no Parse, Submit, Generate or Calculate button. The diff's only `type="submit"` is inside a test asserting there is none, and there is no `<form>` or multi-step flow.
  - Confirm actions exist only for values read from messy input ("Mark as approved/rejected", tapping a balance candidate).
  - The free-form date pickers are untouched.
- **Accessibility, measured in Chromium at 1440, 768, 375 and 320 with deviceScaleFactor 1:**
  - No horizontal overflow on either page at any width.
  - All new text is at least 12 px. The lowest contrast in the new blocks is 6.12:1, so all pass WCAG AA.
  - Every new interactive control is at least 44 px; the only items under 44 px are text `<label>`s and the pre-existing guard checkboxes, which sit inside 44 px labels.
  - Every new input has a label, and headings run h2 → h3.
  - With the keyboard you can reach Apple, Google, Outlook, the link field and "Copy calendar link" in both blocks, as well as the rescue link, Dismiss, the file picker (focus-within ring), "Paste the text instead", the candidates, "Mark as approved", the out-of-office download, the out-of-office textarea and "Copy message". Each shows a 2px ink outline offset 2px.
  - After confirming, focus moves to the "Marked as approved" heading.
